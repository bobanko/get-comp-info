# Синхронизация с облаком

> Статус: реализовано (`sync-cloud.ps1`, `cloud-client.ps1`). Синхронизация с USB (`sync-usb.ps1`) удалена.

Облако — основной источник данных. Каждая копия программы (на флешке или на компьютере) хранит локальную копию базы в `data` и синхронизирует её только с облаком. Синхронизации флешки напрямую с компьютером нет.

Запуск: пункт «Синхронизировать с облаком» в главном меню или `sync-cloud.BAT`. Скрипт работает с той копией программы, из которой запущен, поэтому синхронизировать флешку можно прямо с неё на любом компьютере с интернетом. Устанавливать или копировать программу на этот компьютер не нужно.

## Ключ доступа

Работать с облаком из консоли могут роли `harvester`, `editor` и `admin` (см. [CLOUD.md](CLOUD.md)). Роль `viewer` пользуется только веб-интерфейсом, ключей у неё нет.

Каждый такой пользователь создаёт себе **личный ключ** в веб-интерфейсе. Ключ показывается один раз, у него есть название (например, «Флешка Сергея»), и его можно отозвать. Права ключа совпадают с правами его владельца.

Где скрипт берёт ключ:

1. Файл `cloud-key.txt` в папке программы. Первая непустая строка считается ключом, пробелы по краям игнорируются.
2. Если файла нет, скрипт просит ввести ключ в консоли. Ввод скрыт (`*`), `Backspace` поддерживается, `Esc` отменяет синхронизацию.

После успешной проверки введённого ключа (`GET /me`) скрипт предлагает сохранить его (стрелки и `Enter`):

- **Сохранить ключ в этой копии программы** — ключ записывается в `cloud-key.txt`, и больше вводить его не нужно;
- **Не сохранять** — ключ используется только в текущем запуске.

Перед выбором показывается предупреждение: тот, кто получит флешку с сохранённым ключом, сможет синхронизироваться от вашего имени. Если такая флешка потеряна, сразу отзовите ключ в веб-интерфейсе. Неверный ключ сохранить не предлагается. Файл исключён из Git.

Если ключ неверный или отозван, скрипт показывает красное сообщение и предлагает ввести ключ ещё раз. Если не подошёл ключ из файла, после ввода правильного ключа скрипт предлагает заменить им содержимое файла.

## Настройки

`cloud-config.json` в папке программы, хранится в Git и не содержит секретов:

```json
{
  "apiUrl": "https://comp-info.example.com/api/client"
}
```

## Порядок синхронизации

Один запуск выполняет все шаги по порядку.

1. **Проверка доступа.** `GET /me` возвращает имя пользователя и роль. На экране показываются пользователь, роль и адрес облака.
2. **Миграция старых отметок.** У локальных записей удаляются поля `addedToExternalDatabase` и `addedToExternalDatabaseAt` (см. «Статус записи»). Само по себе это не считается изменением записи и не отправляется отдельно.
3. **Отправка изменений.** Отправляются локальные записи, которые новые для облака или изменились с последней синхронизации. Каждая отправка содержит `baseRevision` — ревизию облачной версии, на которой основано локальное изменение (для новой записи `null`).
   - Облако не менялось с `baseRevision` — запись принимается, ревизия увеличивается.
   - Содержимое совпадает с облачным — новая ревизия не создаётся, локальное состояние просто обновляется.
   - Облако менялось — **конфликт** (см. ниже).
4. **Загрузка базы.** Скрипт получает все записи, изменённые в облаке после прошлой синхронизации (при первой синхронизации — все), и записывает их в `data`. Локально изменённые записи, которые не удалось отправить, не перезаписываются: они остаются в статусе «Изменено» до следующей синхронизации.
5. **Итог.** Показываются количества: отправлено новых, отправлено изменённых, совпало с облаком, получено новых, обновлено из облака, удалено по облаку, конфликтов отложено, а также ошибки по отдельным файлам. Если в облаке есть более новая версия программы, в конце показывается подсказка запустить «Обновить программу» (ошибка этой проверки синхронизацию не прерывает).

Роли `harvester`, `editor` и `admin` синхронизируются из консоли одинаково. Разница между ними только в правах в веб-интерфейсе.

## Конфликты

Конфликт возникает, когда одну запись изменили и локально, и в облаке. Например, флешка неделю собирала данные без интернета, а за это время коллега поправил комментарий в вебе.

Скрипт показывает знакомую таблицу «Поле | Локально | В облаке». Отличающиеся строки выделены жёлтым, совпадающие серым, в заголовке видно, кто и когда изменил облачную версию. Действия (стрелки и `Enter`):

- **Выбрать значения по полям** — для каждого отличающегося поля выбрать облачное или локальное значение. `Esc` возвращает к предыдущему полю.
- **Оставить версию из облака** — локальная запись заменяется облачной.
- **Отправить локальную версию** — локальная запись заменяет облачную. Старая версия остаётся в истории облака.
- **Отложить** — запись остаётся в статусе «Изменено» и будет разобрана при следующей синхронизации.

Перед сохранением показывается итоговая таблица «В облаке | После сохранения» с подтверждением. Результат разбора отправляется как обычное изменение с актуальной `baseRevision`. Если за время разбора облако снова изменилось, разбор повторяется.

## Удаление записей

Удалять записи в облаке может только `admin` через веб-интерфейс. При загрузке базы удалённые записи убираются из локального `data`. Исключение — записи, изменённые локально после последней синхронизации: для них скрипт спрашивает, восстановить запись в облаке или удалить локально.

Локальное удаление JSON-файла **не удаляет** запись в облаке. Файл снова появится при следующей загрузке.

## Статус записи (бывшая отметка «БД»)

Ручная отметка «добавлено во внешнюю базу» (клавиша `A` в просмотрщике) упраздняется. Колонка «БД» в просмотрщике заменяется колонкой «Облако», статус в ней вычисляется автоматически:

| Статус | Цвет | Значение |
|---|---|---|
| `В облаке` | `Green` | Локальная запись совпадает с последней синхронизированной облачной версией |
| `Изменено` | `Yellow` | Запись есть в облаке, но изменена локально после последней синхронизации |
| `Нет в облаке` | `DarkYellow` | Запись ещё ни разу не отправлялась в облако |

Статус показывает состояние на момент последней синхронизации этой копии. Без интернета он не проверяет, что происходит в облаке сейчас. Сортировка по колонке и экспорт CSV используют этот статус.

Старые значения `addedToExternalDatabase` и `addedToExternalDatabaseAt` сбрасываются: поля удаляются из записей при синхронизации, облако их не принимает. Просмотрщик их игнорирует.

## Локальное состояние

`cloud-state.json` в папке программы хранит состояние именно этой копии (исключён из Git):

```json
{
  "apiUrl": "https://comp-info.example.com/api/client",
  "cursor": 1842,
  "lastSyncAt": "2026-10-23T14:05:12+03:00",
  "records": {
    "03341FE8-9B79-4CC9-8CBD-A82BDD18C277": {
      "file": "03341FE8-9B79-4CC9-8CBD-A82BDD18C277.json",
      "revision": 7,
      "hash": "<SHA256 канонического JSON, записанного при последней синхронизации>"
    }
  }
}
```

- `cursor` — номер последнего полученного изменения в облаке, чтобы загружать только новое.
- `revision` и `hash` для каждой записи нужны для вычисления статуса и `baseRevision`. Хеш считается от канонического JSON (порядок ключей и форматирование не важны) той функцией, которая уже есть в `sync-merge.ps1`.
- Если `apiUrl` в состоянии не совпадает с `cloud-config.json`, состояние считается пустым, и копия синхронизируется заново как в первый раз. При этом локальные данные не теряются: совпадающие записи распознаются по содержимому.
- Удаление `cloud-state.json` безопасно. Следующая синхронизация сравнит все записи с облаком: совпадающие получат статус «В облаке», отличающиеся будут разобраны как конфликты.

## Первичная загрузка данных

Отдельного импорта нет. Первая синхронизация любой копии с существующими данными (флешки или компьютера) отправляет все её записи в облако как новые. Если та же запись уже пришла в облако с другой копии, совпадающее содержимое просто принимается, а отличия разбираются как конфликт.

Для старых записей без `computerId` идентификатором в облаке служит имя файла без `.json`.

Записи, впервые полученные из облака, сохраняются в файл `<идентификатор>.json`; недопустимые в именах файлов символы заменяются на `_`, точки и пробелы сохраняются. Поэтому одна и та же запись может называться по-разному на разных копиях: например, старый файл `PF58Y8F9.json` с `computerId` внутри на другой копии появится как `<computerId>.json`. Запись определяется по идентификатору, а не по имени файла.

## Сеть и надёжность

- Включается TLS 1.2 (`[Net.ServicePointManager]::SecurityProtocol`), это обязательно для Windows PowerShell 5.1.
- Используется системный прокси с учётными данными текущего пользователя.
- Если облако недоступно, показывается понятное сообщение. Локальные данные не меняются, код завершения — 1.
- Каждая запись сохраняется в `data` через временный файл с заменой. `cloud-state.json` обновляется после каждой успешно обработанной записи, поэтому прерванную синхронизацию можно просто запустить снова.
- Ошибочный JSON в `data` останавливает отправку этого файла с указанием имени, остальные записи обрабатываются.
- Если у нескольких файлов один идентификатор, запись пропускается целиком (и отправка, и загрузка) с ошибкой, где перечислены файлы. Оставьте один файл и запустите синхронизацию снова.
- Идентификатор в адресе запроса экранируется полностью, включая точки: Windows PowerShell 5.1 иначе молча отрезает точку в конце (`To be filled by O.E.M.`).
- Перед запуском синхронизации закройте сборщик и просмотрщик.

## Программа на флешке

Синхронизация с облаком переносит **только данные**. Раньше `sync-usb.ps1` заодно обновлял на флешке файлы программы. Теперь для этого есть отдельный пункт меню «Обновить программу»: новые версии скачиваются из облака по тому же личному ключу ([PROGRAM_UPDATE.md](PROGRAM_UPDATE.md)).

Код работы с облаком (настройки, ключ, TLS, запросы) общий для синхронизации и обновления и находится в `cloud-client.ps1`.
